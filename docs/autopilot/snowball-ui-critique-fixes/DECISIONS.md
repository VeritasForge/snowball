# 판단 기록 — 스노우볼 critique 후속 수정

## 판단 #1 — 자율 실행 중 커밋하지 않는다
- 상황: autopilot 스킬은 의미 단위마다 커밋하라고 하지만, 이 프로젝트와 세션 규칙은 사용자가 요청할 때만 커밋하라고 한다.
- 중요도: 중간
- 확인한 출처: autopilot SKILL §10, CLAUDE.md git 규칙, 세션 지침
- 원래 물으려던 것: 단계마다 자동 커밋해도 되는가
- 세운 가정: 커밋 권한은 위임되지 않았다. 변경은 작업 트리에 남기고 마지막에 한 번에 보고한다.
- 결정: 커밋·푸시 모두 하지 않는다
- 근거: 되돌리기 쉬운 쪽(커밋 없음)이 안전하고, 사용자가 원하면 마지막에 단계별로 나눠 커밋할 수 있다.

## 판단 #2 — 투자 자산·보유 현금 카드의 색 띠를 중립색(border-muted)으로
- 상황: 두 띠가 success(초록)·warning(앰버)인데 DESIGN.md는 success를 "100% 달성과 체결"로 정의한다.
- 중요도: 중간
- 확인한 출처: DESIGN.md Colors, SummarySection.tsx, 기존 SummarySection 테스트(손익 띠만 단정)
- 원래 물으려던 것: 두 띠를 어떤 색으로 바꿀지
- 세운 가정: 금액 카드는 의미 신호가 아니므로 중립(Fog Grey)이 맞다. 금색은 "신호" 전용이라 쓰지 않는다.
- 결정: border-muted. 현금 입력창 밑줄(border-warning)은 이번에 손대지 않음(입력 경계는 접근성 단계에서 다룸)
- 근거: 의미 색을 의미 없는 곳에 쓰지 않는다는 DESIGN.md 원칙. 클래스 한 개 교체라 되돌리기 쉽다. 반대 담당 경합은 생략(규칙이 답하는 사안이고 비용이 작다).

## 판단 #3 — Toast 에러 글자색은 이번에 바꾸지 않는다
- 상황: 에러 토스트가 코랄 배경에 흰 글자(2.78:1)인데 기존 테스트가 text-white를 명시적으로 단정한다.
- 중요도: 중간
- 확인한 출처: Toast.tsx, Toast.test.tsx
- 원래 물으려던 것: 기존 테스트의 text-white 단정을 text-accent-foreground로 바꿔도 되는가
- 세운 가정: 프로젝트 규칙상 기존 테스트 수정은 승인이 필요하다.
- 결정: 보류. 최종 보고에 올린다.
- 근거: 테스트 주석이 "빨강 위 흰 텍스트 대비"를 의도로 적었으나 계산상 2.78:1로 AA(4.5:1) 미달이다.

## 판단 #4 — 카테고리 색 분리는 사용자 결정으로 보류
- 상황: 칩(bg-danger 등 토큰)과 도넛(#ef4444 등 Tailwind hex)이 서로 다른 값이고, 둘 다 코랄·보라를 손익/매수·매도와 공유한다.
- 중요도: 높음
- 확인한 출처: CategorySelector.tsx, DonutChart.tsx
- 원래 물으려던 것: 카테고리 5색을 어떤 팔레트로 쓸지
- 세운 가정: 팔레트는 디자인 방향 결정이라 임의로 정하지 않는다.
- 결정: 보류
- 근거: 새 색 5개를 만드는 일이라 DESIGN.md 토큰 추가가 필요하고, 사용자 취향이 갈린다.

## 판단 #5 — 계좌 탭에 tablist 대신 aria-current와 그룹 이름을 쓴다
- 상황: critique는 tablist/aria-selected를 제안했지만 연결된 tabpanel이 없고 방향키 이동도 구현하지 않았다.
- 중요도: 중간
- 확인한 출처: AccountTabs.tsx, 기존 테스트(getByText 기반이라 영향 없음)
- 원래 물으려던 것: critique 제안대로 tablist로 갈지
- 세운 가정: 반쪽짜리 tab 의미는 스크린리더 사용자에게 방향키가 동작한다는 잘못된 기대를 준다.
- 결정: role="group" aria-label="계좌 선택" + 현재 계좌에 aria-current="true"
- 근거: 실제 동작과 일치하는 의미만 부여한다. 나중에 방향키 이동을 만들면 tablist로 올릴 수 있다.

## 판단 #6 — 손실 글자 대비 수정은 기존 테스트 수정이 필요해 보류
- 상황: 손실 텍스트가 text-primary(보라 3.34:1)인데, 기존 테스트 2곳이 text-primary 클래스를 단정한다. 해결책(예: #9B8FFF, 6.26:1)은 새 토큰이 필요하다.
- 중요도: 높음
- 확인한 출처: AssetRow.test.tsx:73, SummarySection.test.tsx:32, 대비 계산
- 원래 물으려던 것: 두 테스트의 클래스 단정을 새 토큰 클래스로 바꿔도 되는가
- 세운 가정: 프로젝트 규칙상 기존 테스트 수정은 승인 필요. 클래스 우회(text-primary와 다른 색을 동시에 걸기)는 테스트를 속이는 편법이라 쓰지 않는다.
- 결정: 보류
- 근거: 동작 의도(음수는 보라 계열)는 유지되고 클래스 이름만 달라지는 변경이지만, 승인 없이 기존 테스트를 고치지 않는다.

## 판단 #7 — 목표 대비 막대(B)는 도넛을 지우지 않고 추가
- 상황: 사용자가 "A와 B를 다 구현"을 선택했다. B를 "도넛을 막대로 교체"로 정의했으나, 교체하면 DonutChart 테스트 삭제가 필요하다.
- 중요도: 높음
- 확인한 출처: tests/components/DonutChart.test.tsx, CLAUDE.md Test Protection Protocol
- 원래 물으려던 것: 도넛 차트와 그 테스트를 삭제해도 되는가
- 세운 가정: 기존 테스트 삭제는 승인이 필요하므로, 막대(TargetBars)를 도넛 위에 추가하고 도넛은 유지한다.
- 결정: TargetBars 추가, DonutChart 유지. 삭제 여부는 사용자 결정으로 남긴다.

## 판단 #8 — 표 폭 확보를 위해 보조 패널을 2xl 이상에서만 옆에 배치
- 상황: 1440px에서 우측 550px 패널 때문에 표가 약 620px로 좁아져 행동 열 머리글이 글자 단위로 줄바꿈되었다.
- 원래 물으려던 것: 보조 패널을 표 아래로 내려도 되는가
- 세운 가정: 핵심 작업 영역은 표이므로 표 폭이 우선이다. 1536px 미만에서는 표 아래에 막대와 도넛을 2열로 둔다.
- 결정: xl → 2xl 로 변경

## 판단 #9 — 목표 대비 비중 패널 제거 (사용자 결정)
- 상황: 사용자가 화면을 보고 "평가금액 칸에 편차가 있으니 따로 표현할 필요 없다"고 판단했다.
- 결정: TargetBars 컴포넌트와 그 테스트, Home 통합 테스트 1건을 삭제했다(모두 이번 작업에서 새로 만든 것). 도넛은 유지하고 DeviationBar는 표 행에서 계속 쓴다. 판단 #7의 "도넛 삭제 여부"는 사실상 해소: 도넛은 유지.
